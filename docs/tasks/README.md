# 작업 지시서 (docs/tasks/)

G-MOIM 프로젝트에서 **외부 AI 세션에 위임하는 작업**의 지시서를 모아둔 곳.

---

## 왜 지시서를 따로 두나

설계 결정 문서 전체를 통째로 주면 두 가지가 나빠진다.

1. 맥락이 너무 많으면 작업자가 **설계 결정에 개입하려 든다.** 결정들은 서로 물려 있어서 일부만 아는 상태의 개입은 앞의 전제를 깬다
2. 토큰과 시간이 낭비된다

그래서 작업마다 **필요한 조각만 잘라낸 자립형 지시서**를 만든다. 지시서 하나만 읽으면 작업이 가능해야 한다.

---

## 위임 판단 기준

넘길 것 — 맥락이 필요 없고, 양이 많고, 검증이 쉬운 일.

넘기지 말 것 — 설계 결정. 앞의 결정들과 얽혀 있어 전제를 통째로 옮겨야 하는 일. 설명 시간이 작업 시간보다 길어진다.

---

## 작업 흐름

```
1. 지시서를 외부 AI 세션에 붙여넣는다 (파일 전체)
2. AI가 산출물을 생성한다
3. 지시서의 "검증" 항목으로 결과를 확인한다
4. 지정된 경로에 커밋한다
5. 지시서 하단 "진행 기록"에 한 줄 남긴다
```

**AI에게 커밋을 시키지 않는다.** 권한이 없고, 있어도 검증 없이 들어가면 안 된다.

## 레포 구조

```
G-MOIM/
├── docs/
│   ├── design/       설계 문서 (버전별)
│   ├── journal/      개발 일지 (날짜별)
│   ├── infra/        인프라 확장 플랜
│   └── tasks/        이 폴더
└── data/
    ├── kits/         킷 DB 수집 결과
    └── aliases/      별칭 사전
```

드라이브 `G-MOIM/` 폴더의 내용을 이 구조로 이관 예정. 이관 후에는 레포가 SSOT가 되고 드라이브는 폐기한다.

## 지시서 작성 규칙

새 지시서를 만들 때 아래를 반드시 포함한다.

- **목적** — 왜 이걸 하는지 한 문단. 판단이 필요할 때 기준이 된다
- **절대 제약** — 어기면 결과물 전체를 버려야 하는 것
- **출력 형식** — 컬럼, 타입, 파일 경로까지 명시
- **예외 처리** — 애매한 케이스를 어떻게 할지 미리 정함
- **검증** — 결과가 맞는지 확인하는 구체적 방법
- **하지 말 것** — 시키지 않았는데 하기 쉬운 것들
- **진행 기록** — 세션이 끊겨도 이어갈 수 있게
