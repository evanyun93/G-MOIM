# 벤더 선택지 및 이전 시나리오 v1

규모 변화에 따라 Cloudflare / Neon 구성을 바꿔야 할 때의 경우의 수.

작성 2026-09-12 · 가격 정보 확인 2026-09-12

> **주의** — 가격과 무료 티어는 자주 바뀐다. 실제 결정 전에 공식 페이지 재확인 필수. 특히 이 문서는 "지금 고르는 법"이 아니라 "나중에 무엇을 검토할지"의 목록이다.

---

## 1. 먼저, 언제 이 문서를 읽나

**대부분의 경우 읽을 필요가 없다.** 인프라확장플랜의 0~2단계, 즉 월 $45 이하 구간에서는 Cloudflare + Neon 조합을 바꿀 이유가 사실상 없다. R2의 egress 무료가 이미지 커뮤니티에 주는 이점이 워낙 커서, 다른 벤더로 옮길 유인이 잘 안 생긴다.

이 문서가 필요해지는 건 아래 중 하나가 발생했을 때다.

- 월 인프라 비용이 $300을 넘어섰다
- 특정 기능이 Cloudflare 생태계에서 안 된다 (장시간 실행 작업, 무거운 이미지 처리 등)
- 벤더가 정책을 바꿔서 조건이 나빠졌다
- 법인 전환·투자 유치로 요구사항이 달라졌다

## 2. 레이어별 선택지

### 2.1 이미지 스토리지 — 가장 안 바꾸는 게 좋은 레이어

| 옵션 | egress | 특징 | 이전 난이도 |
|---|---|---|---|
| **Cloudflare R2** (현재) | **무료** | S3 호환 API, CDN 통합 | — |
| AWS S3 | GB당 과금 | 생태계 최강, 하지만 egress가 치명적 | 중 |
| Backblaze B2 | Cloudflare 경유 시 무료 | R2보다 저장 단가가 약간 쌈 | 중 |
| Wasabi | 무료(정책 제한 있음) | 정액제, 최소 저장 기간 조건 | 중 |

**결론 — 바꿀 이유가 거의 없다.** 이미지 커뮤니티에서 egress 과금은 곧 트래픽이 늘수록 적자라는 뜻이고, 그게 설계 문서 부록 C의 출발점이었다. S3로 가는 유일한 명분은 AWS의 다른 서비스와 깊게 엮여야 할 때인데, 그때도 이미지만 R2에 남기는 하이브리드가 가능하다.

**S3 호환 API를 쓰는 것이 보험이다.** R2가 S3 호환이므로 코드 수정 없이 엔드포인트만 바꿔 이전할 수 있다. 벤더 고유 SDK를 쓰지 말 것.

### 2.2 컴퓨트 / 호스팅

| 옵션 | 모델 | 강점 | 약점 |
|---|---|---|---|
| **Cloudflare Workers/Pages** (현재) | 엣지 서버리스 | 정적 무제한, 저렴, R2 통합 | CPU 시간 제한, 장시간 작업 불가, Node API 일부 미지원 |
| Vercel | 서버리스 + ISR | Next.js ISR이 가장 매끄러움 | 대역폭 과금, 팀 좌석 비용 |
| Fly.io | 컨테이너 | 일반 서버처럼 씀, scale-to-zero | 직접 관리할 게 늘어남 |
| Railway / Render | 컨테이너 PaaS | 설정이 단순 | 유휴 비용 |
| AWS (ECS/Lambda + CloudFront) | 종합 | 무엇이든 가능 | 복잡도와 비용 관리 부담이 큼 |

**Cloudflare를 떠나야 하는 구체적 신호**

- 킷 DB 수집·정제 배치가 Workers CPU 제한에 걸림 → 이건 컴퓨트 이전이 아니라 **배치만 분리**하면 된다. 로컬이나 GitHub Actions에서 돌리고 결과만 DB에 넣는 방식
- 이미지 변환을 서버에서 무겁게 해야 함 → Cloudflare Images 유료를 쓰거나, 변환만 별도 컨테이너로 분리
- ISR이 필요한데 지원이 부족 → Vercel 검토 대상. 다만 대역폭 과금이라 이미지가 R2/CDN에서 나가도록 분리해야 함

**핵심** — 컴퓨트 전체를 옮기기 전에 **문제가 되는 작업만 떼어내는** 방법을 먼저 검토할 것. 대부분 그걸로 해결된다.

### 2.3 데이터베이스

| 옵션 | 모델 | 무료 티어 | 유료 시작 | 비고 |
|---|---|---|---|---|
| **Neon** (현재 권장) | 서버리스 Postgres, scale-to-zero | 프로젝트당 0.5GB, 100 CU-h/월 | Launch 약 $19/월 | 브랜칭, Databricks 소유 |
| Supabase | Postgres + 인증·스토리지·실시간 | 2프로젝트, 500MB, 1주 무활동 시 정지 | Pro $25/월 | 붙일 게 적음, 상시 가동 |
| PlanetScale | 분산 SQL | 없음(트라이얼) | 단일노드 약 $23/월 | 스케일 강점 |
| AWS RDS / Aurora | 관리형 | 프리티어 12개월 | 상시 과금 | 예측 가능, 비쌈 |
| 직접 운영 (VPS + Postgres) | 셀프 | — | VPS 비용만 | **네 경력상 가장 유리한 옵션** |

**직접 운영에 대해**

대부분의 개인 개발자에게는 권하지 않지만, 대용량 PostgreSQL 운영과 튜닝이 본업이었다면 얘기가 다르다. 월 $50짜리 VPS 한 대가 관리형 $300짜리 플랜을 이길 수 있다. 다만 조건이 있다.

- 백업과 복구를 반드시 자동화하고, **복구를 실제로 테스트**할 것. 백업이 있다고 믿는 것과 복구가 되는 것은 다르다
- 보안 패치 주기를 정해둘 것
- 단일 장애점이 되므로, 커뮤니티가 실제 유저를 갖게 된 뒤에는 이중화 계획이 필요

**전환 시점 판단** — 관리형 비용이 월 $100을 넘고, 그 비용의 대부분이 컴퓨트라면 직접 운영을 검토할 값어치가 있다. 그 아래에서는 관리형이 시간 대비 이득이다.

### 2.4 검색

| 단계 | 방식 |
|---|---|
| 지금~중기 | Postgres + pg_trgm + `alias` 테이블 (#40. Neon은 pg_bigm 미지원, 2026-09-14 확인) |
| 부하 발생 시 | Meilisearch (셀프호스팅, 가벼움) 또는 Typesense |
| 대규모 | Elasticsearch / OpenSearch |

Elasticsearch는 상시 메모리 요구가 커서 개인 프로젝트 규모에서는 거의 항상 과잉이다. Meilisearch가 중간 단계로 적절하다.

### 2.5 조회 분석 (2026-09-14 추가, #39)

| 단계 | 방식 |
|---|---|
| 지금 | Cloudflare Web Analytics + 일 배치로 `daily_metrics` 스냅샷 |
| 옮길 때 | Umami·Plausible 등. 스크립트와 배치 읽기 함수만 교체 |

과거 수치는 우리 DB에 있어 이관할 데이터가 없다. 교체일 기준 수치 불연속만 기록한다.

## 3. AWS로 가야 하는 경우

**결론부터 — 당분간 갈 이유가 없다.** 다만 아래 상황에서는 검토 대상이 된다.

| 상황 | AWS가 답인가 |
|---|---|
| 비용이 커졌다 | **아니다.** 대개 AWS가 더 비싸다. 특히 egress |
| 트래픽이 커졌다 | **아니다.** Cloudflare가 대역폭에서 유리 |
| 복잡한 백엔드 작업이 필요하다 | 부분적으로. 해당 작업만 Lambda/ECS로 분리 가능 |
| 법인 전환 후 규정 준수 요구 | 그렇다. 감사·인증 요구가 붙으면 AWS 생태계가 유리 |
| 투자 유치 후 크레딧을 받았다 | 그렇다. 크레딧 규모가 크면 경제성이 뒤집힘 |
| 팀이 늘어 AWS 경험자가 합류 | 그렇다. 운영 인력의 익숙함이 비용보다 클 수 있음 |

**AWS 스타트업 크레딧과 Cloudflare 크레딧 프로그램이 둘 다 존재한다.** 사업화 단계에 들어가면 신청 조건을 확인할 것. 크레딧이 붙으면 위 표의 판단이 대부분 뒤집힌다.

## 4. 이전 난이도와 준비

| 레이어 | 이전 난이도 | 미리 해둘 것 |
|---|---|---|
| 이미지 스토리지 | 중 (데이터 이관 + URL) | S3 호환 API만 사용. 벤더 SDK 금지 |
| DB | 낮 (Postgres → Postgres) | 벤더 고유 확장 기능 의존 최소화 |
| 컴퓨트 | 중~높 (런타임 차이) | 엣지 런타임 고유 API 사용 최소화, 비즈니스 로직을 프레임워크에서 분리 |
| CDN | 낮 | — |
| 인증 | **높음** | 벤더 인증(Supabase Auth 등)에 묶이면 이전이 어려움 |

**인증이 가장 큰 잠금 요소다.** Supabase Auth나 Neon Auth를 쓰면 편하지만, 유저 테이블이 벤더 쪽에 있으면 나중에 옮길 때 전원 재가입 또는 복잡한 마이그레이션이 필요하다.

완화책 — 벤더 인증을 쓰더라도 **자체 `users` 테이블을 두고 벤더 ID를 외래키로만 참조**할 것. 프로필, 권한, 활동 이력 등 실제 데이터는 자체 테이블에 둔다. 그러면 인증 제공자만 교체하면 된다.

## 5. 판단 순서 (문제가 생겼을 때)

1. **정말 인프라 문제인가?** 쿼리 하나, 인덱스 하나, 캐시 설정 하나가 원인인 경우가 대부분이다
2. **한 레이어만 바꿔서 되나?** 전체 이전 전에 병목 레이어만 교체
3. **문제 작업만 떼어낼 수 있나?** 배치, 이미지 변환, 검색은 분리 가능
4. **그래도 안 되면** 이 문서의 표에서 해당 레이어의 대안을 검토
5. **이전 결정 시** 데이터 이관 시간, URL 변경 여부, 다운타임을 먼저 계산할 것
