## 1. 프로젝트 정의

**한 줄 정의**
한 달 걸려 만든 작례를 올릴 마땅한 곳이 국내에 없다. 그 자리를 만든다.

**핵심 차별점**
기존 플랫폼은 흐름과 축적 중 하나만 갖고 있고, 구조상 나머지 하나를 붙일 수 없다.

| | 흐름(실시간 소통) | 축적(개인 아카이브) |
|---|---|---|
| 디시 건담갤 | 있음 | 없음 — 갤로그는 시간순 나열뿐 |
| 네이버 블로그 | 없음 — 댓글이 전부 | 있음 — 카테고리, 앨범형 |
| **G-MOIM** | **있음** | **있음** |

**목적 우선순위**
1순위 포트폴리오와 재미 → 2순위 수익화(광고, 멤버십). 수익화는 반드시 고려하되 초기 설계를 왜곡시키지 않는다.

**MVP 범위** (결정 #11)
킷 DB(위키) + 개인 블로그 + 계정. 커뮤니티 게시판(갤)은 제외. 신고 창구는 법적 요건이라 포함.

**소유권 구분** (혼동 방지)

| | 소유 | 수정 권한 | 위치 |
|---|---|---|---|
| 작례 | 유저 개인 | 작성자만 | 개인 블로그 |
| 이미지 | 유저 개인 (#24) | 업로드한 유저만 | 게시물이 참조 |
| 킷 DB | 공용 | 수정 제안 수용 | 위키 |

`post_kits`는 작례를 킷 쪽으로 옮기거나 복제하지 않는다. 참조 하나를 거는 것뿐이다.

## 2. 확정 결정 로그

### #1 갤과 블로그는 분리한다
갤 글과 블로그 포스트는 별개 객체. 블로그에 작례를 올리고 갤에 공유하는 흐름.

근거 — 두 글의 성격이 실제로 다르다. 블로그 글은 긴 제작기에 사진 여러 장, 편집이 필요한 "작품". 갤 글은 짧고 즉흥적인 "대화". 에디터부터 달라야 하는 물건을 한 테이블에 넣을 이유가 없다. 아카이브 순도가 자동으로 보장된다.

부대 조건 — 네이버가 실패한 이유는 분리 자체가 아니라 카페와 블로그가 다른 서비스라 동선이 끊긴 것. 같은 계정 안에서 갤 ↔ 블로그 동선을 촘촘히 깔아야 이 결정이 성립한다.

### #2 공유 글은 링크 카드, 댓글은 블로그에 일원화
갤에 공유된 작례는 썸네일과 제목만. 댓글은 블로그 포스트에만.

근거 — 작품에 대한 반응이 작품 아래 영구히 쌓여야 아카이브 가치가 생긴다. 갤은 유입 경로 역할.

파생 — 링크 카드의 유일한 상호작용이 추천이 된다. 따라서 추천 → 개념글 경로가 작례의 유입 엔진. 1.2.2 설계 시 반영할 것.

### #3 킷 DB를 첫 진입 가치이자 데이터 뼈대로 삼는다
반다이 킷 카탈로그를 먼저 구축하고 그 위에 작례·적산·알림을 얹는다.

근거 — 유저가 0명이어도 성립하는 유일한 후보. 동시에 적산 관리와 재입고 알림의 전제 조건.

### #4 범위는 건프라 한정
건담 시리즈 프라모델만. 전 등급, 구판 포함. 반다이 타 라인(마크로스, 30MM, 피규어라이즈 등)과 타 메이커 제외.

근거 — 혼자 완성 가능한 크기여야 한다. 스키마만 확장 가능하게 짜두면 나중에 열 수 있다.

### #5 위키 기반으로 전 등급 얕게 깔고 점진 보완
자동 수집으로 커버리지를 먼저 확보, 상세는 나중에 채운다.

근거 — 킷 DB는 검색해서 쓰는 물건이라 커버리지가 곧 유용성. HG를 배제하는 비용(유저 대다수가 자기 킷을 못 찾음)이 얕은 데이터의 비용보다 크다.

필수 부대 조건:

- 작례 0개 킷 페이지는 `noindex`. 기준은 하드코딩하지 말고 `is_indexable` 계산 컬럼으로 조정 가능하게
- 빈 페이지는 "이 킷의 첫 작례를 등록해보세요" CTA로 전환
- 자동 수집분은 "미검증" 표시 + 유저 수정 제안 수용
- **사실 필드만 추출하고 서술 텍스트는 수집 금지.** 제품명·등급·스케일·발매일·정가는 저작권 대상이 아니나, 위키 설명 문장은 CC BY-SA가 적용되고 전염성이 있음. 나무위키는 비영리 조건이므로 광고 계획이 있으면 소스에서 제외

부속 — 킷 페이지 대표 이미지는 박스아트가 아니라 **유저 작례**로 채운다. 반다이 저작물 문제가 사라지고, 킷 페이지가 이 사이트에만 있는 얼굴을 갖고, "내 작례가 그 킷의 대표 이미지가 된다"가 업로드 동기가 된다. 초기에는 운영자 작례로.

### #6 킷과 기체를 M:N으로 분리한다
`kit`, `unit`, 조인 테이블 `kit_units(is_primary)`.

근거 — 조인 테이블 비용이 사실상 없는데 1:N은 세트 킷·무장 세트에서 예외 처리가 계속 쌓인다. 위키 원본이 정형이 아닌 것도 M:N에 유리.

부수 효과 — 기체 페이지가 생긴다. RX-78-2 페이지 하나에 EG부터 PG까지 전 등급 킷과 작례가 모인다. 킷 페이지보다 두껍고 검색 가치도 높다.

### #7 재판은 릴리스 이력으로, 변형은 연결된 별개 킷으로
`kit_releases`로 재판 이력(발매일, 정가, 품번)을 분리. 재판은 페이지를 만들지 않는다. 외형·유통 변형은 별개 `kit` + `base_kit_id` 연결. 킷 페이지에 "변형 포함" 토글.

근거 — 재판 분리는 논쟁 여지가 없고 페이지 수를 줄여 결정 #5의 빈 페이지 우려를 완화. 정가 인상 이력이 남아 나중에 시세 기능에 재활용 가능. 외형 변형은 사진상 명백히 다른 물건이라 페이지 분리가 맞다.

**수정 (v3 반영)** — `kit_releases`를 MVP 수집 범위에 포함한다. 수집 스키마에 재판 자리가 없으니 초판·재판 정보가 한 행에 섞여 들어왔다(재판 품번이 초판 행에 기입됨). 품번·발매일·정가는 `kit`에서 빼고 `kit_releases`에만 둔다.

### #8 등급은 grade_family 단일 계층
`HG / RG / MG / MGEX / MGSD / PG / EG / RE100 / FM / SD / 구판`. 작품 접미어(HGUC의 UC, HGWFM의 WFM)는 등급에 포함하지 않는다.

근거 — 접미어는 `series`와 정보가 중복됨. 필터는 등급 × 작품 조합으로 해결. 검색은 `name_ko` 전문 검색과 `alias`로 커버.

MGSD는 독립 family — 프로포션은 SD, 구조와 색분할은 MG 계열이라 어느 쪽에 종속시켜도 필터가 오염된다.

보류 — PG Unleashed는 일단 PG에, SDCS는 일단 SD에. 데이터 채우다 걸리면 그때 독립. 마스터 테이블이라 재분류 비용이 낮다.

스케일 — 등급에서 유도하지 않는다. HG 1/100(00 시리즈)처럼 변칙이 실재하며, 이를 DB에서 빼는 것은 결정 #5의 커버리지 원칙과 충돌한다. `grade_family.default_scale`은 입력 보조용, `kit.scale`이 진짜 값.

### #9 포스트가 곧 작례 단위
별도 build 엔티티 없음. `post_type`(완성작례/제작기/리뷰/팁/일반)으로 구분하고 킷 페이지에는 완성작례만 노출. 연재는 유저가 서로 링크.

근거 — 이미 "블로그에 쓰고 갤에 공유"라는 두 단계가 있다. 세 번째 단계를 얹으면 아무도 안 쓴다. build가 해결하는 문제 대부분은 post_type으로 해소되고, 필요해지면 나중에 얹어도 늦지 않다.

### #10 킷 연결은 선택. 자동 태그 제안은 후속 과제
완성작례도 킷 연결 없이 게시 가능. 강제 장치 없음. 향후 제목·본문에서 킷명을 추출해 후보를 제시하고 유저는 확인만 하는 방식으로 연결률을 올린다.

근거 — 마찰의 정체는 "고르는 수고"이므로, 강제로 누르는 대신 수고 자체를 없애는 쪽이 맞다. 강제 여부는 킷 DB 커버리지가 실측되기 전에는 판단 근거가 없다.

준비 — `post_kits`에 `match_source`, `match_confidence`, `confirmed_at`을 지금 넣어둔다. 나중에 자동 태그를 켤 때 유저가 건 것과 기계가 건 것을 구분해야 한다. 자동 매칭 정확도는 사실상 `alias` 사전 품질이 전부이므로, 킷 DB를 채울 때 별칭을 함께 넣는다.

### #11 MVP는 킷 DB + 블로그 + 계정. 갤 제외
포함 — 킷·기체 페이지와 검색, 개인 블로그(작례 작성·게시), 계정. 운영/거버넌스(설계 트리 2장) 중 신고 창구만 포함.

제외 — 커뮤니티 게시판(1.2 전체), AI 모더레이션, 유저 관리자 제도, 수익화.

근거 — **원문 미기록.** 레포 이관 전 결정이라 요약만 남아 있다. 같은 방향의 기록으로 일지 2026-09-12의 예측 "기능을 다 만들기 전에 지칠 것이다. 그래서 MVP 범위를 실제보다 크게 잡는 게 가장 큰 위험이다"가 있다.

영향 — #2가 댓글을 블로그에 둔다고 했으나 댓글 모델은 1.2.2(MVP 제외 노드)에 묶여 있다. 5장 참조.

### #12 ~~출시를 기한으로 게이팅~~ 폐기
대체 — **배포는 상시, 공개만 별도 판단.** 코드는 계속 배포하고, 홍보·색인 허용은 조건을 따로 본다.

근거 — **원문 미기록.** CLAUDE.md의 실패 패턴 "시점이 다른 조건을 하나로 묶는다. 배포 시점과 공개 시점의 조건은 다르다"가 같은 내용이다.

현재 적용 — 공개 전까지 전체 `noindex`. 비용 어뷰징 방어 체크리스트는 "공개(홍보) 전 전 항목 완료"가 기준이다.

### #13 페이지 성격별로 렌더링 방식을 나눈다

| 페이지 | 방식 | 확정 근거 |
|---|---|---|
| 킷, 기체 | SSG. 일 1회 배치 재빌드 | #18 |
| 작례 | SSR + Workers Cache, 수정 시 태그 무효화 | #18 |
| 홈 피드 | SSR | #13 |
| 글쓰기, 관리 | CSR | #13 |

근거 — 전면 SSR이면 조회마다 무료 Workers 일 10만 요청 한도를 쓴다. 반면 크롤러가 볼 페이지는 서버에서 HTML을 만들어야 한다(부록 F). 두 제약을 페이지 성격별로 나눠 푼다.

정정 — 결정 당시 표현은 "SSG/ISR/SSR/CSR" 네 방식이었다. #18에서 킷·기체를 배치 SSG로 정하면서 ISR 자리가 없어졌다. 5장 참조.

### #14 운영 모니터링은 자체 구축. MVP는 `daily_metrics` 집계만
화면(운영 모니터링 페이지)은 뒤로 미루고 일별 집계 테이블만 첫날부터 쌓는다.

근거 — 일별 스냅샷은 **소급 집계가 불가능하다.** 지나간 날의 수치는 나중에 만들 수 없으니, 보는 화면은 미뤄도 수집은 미룰 수 없다. 외부 분석 도구가 아니라 자체 구축을 고른 근거는 **원문 미기록.**

수집 항목 (이후 결정에서 추가된 것 포함) — 요청 수, 업로드 수·용량, 신규 가입 수, 429 발생 수(#20), HEIC 거부 수(#32). 전일 대비 급증 시 알림(#20).

### #15 확장 파츠는 `parent_kit_id`로 대상 킷에 연결한다
외형 변형과 확장 파츠를 다른 컬럼으로 구분한다.

| 관계 | 컬럼 | 대상 | 기체 연결 |
|---|---|---|---|
| 외형·유통 변형 (클리어, 코팅, 한정 컬러) | `base_kit_id` (#7) | 그 자체로 완제품 | 원본과 같은 기체 |
| 확장 파츠·무장 세트, 완제품이 아닌 파츠 세트 | `parent_kit_id` | 대상 킷에 붙여 쓰는 물건 | 없음 |

근거 — 확장 파츠는 기체가 없어 `kit_units`로 킷 페이지에 붙일 길이 없다. `base_kit_id`는 "변형 포함" 토글(#7)에 쓰이므로 파츠를 여기 넣으면 변형 목록에 파츠가 섞인다. (결정 당시 원문은 없고, 지시서 01_v2의 분류 규칙에서 v3 작성 시 정리했다)

명칭 — 수집 CSV에서는 `parent_kit_temp_id`, DB 컬럼은 `parent_kit_id`.

### #16 `limited_channel`은 필수급으로 수집한다
허용값 — `프리미엄반다이` / `건담베이스` / `이벤트` / `일반`. `is_limited=true`면 채널을 반드시 채운다.

근거 — 이전 수집에서 MG 358종 중 143종(약 40%)이 한정 유통으로 보고됐다. 그 이상의 원문은 **미기록.**

**근거 수치 주의** — 358/143은 파일 없이 숫자만 남은 보고치다(지시서 01b). 이후 재수집한 MG 627행은 반려됐다. 결정은 유지하되 비율은 01b 재작업 결과로 다시 확인한다.

### #17 프레임워크는 Astro
근거 — 페이지별 prerender 지정이 되어 #13의 SSG/SSR 혼합을 한 프로젝트에서 처리한다. Cloudflare가 인수했고 Workers 어댑터와 캐시 제공자가 있다. 에디터처럼 인터랙션이 필요한 곳만 island로 띄운다(#31은 React island).

미확인 — Astro의 Cloudflare 캐시 제공자는 실험 단계다. 구현 초기에 동작을 확인한다.

### #18 킷·기체는 SSG + 일 1회 배치, 작례는 SSR + Workers Cache
작례 수정 시 캐시 태그로 무효화한다. 작례 조회가 요청 한도를 소모하는 것을 알고 택했다.

근거 —
- "Pages 빌드 월 500회" 한도는 Pages Git 연동에만 걸려 병목이 아니었다. 정적 에셋 요청은 무료·무제한이고 Worker를 호출하지 않는다
- 대신 배포당 정적 파일 2만 개(무료) 한도가 있어 작례까지 SSG로 만들 수는 없다
- **Workers Cache 적중은 CPU를 쓰지 않지만 요청 수로는 차감된다.** 일 10만 요청은 인프라확장플랜 1단계(월 $5) 트리거와 같은 지점이라, 거기 닿으면 이미 트래픽이 붙은 상태다. 검색 유입이 몰릴 킷·기체 페이지는 계속 무료다

반대 의견 — 작례도 정적 파일로 배치 생성하면 조회가 무료·무제한이다. → 새 글 반영 지연, 2만 개 한도, 수정 시 재빌드가 붙는다. 월 $5를 아끼는 대가로는 크다.

대가 — 킷·기체 페이지의 작례 갤러리는 최대 하루 늦게 갱신된다.

기록 — 이 결정은 두 번의 벤더 문서 오독 위에서 정정됐다(일지 2026-09-13 #8, #10). 한도 수치가 어느 제품에 걸리는지, "실행 안 함"이 "과금 안 함"인지를 구분해 읽어야 한다.

### #19 이식성 — 어떤 인프라가 막혀도 옮길 수 있게
원칙:
- DB는 **벤더 밖에 일 1회 자동 백업**하고, 정기적으로 다른 Postgres에 복구해 행 수를 대조한다. 복구해보지 않은 백업은 없는 것으로 본다
- DB는 표준 Postgres 기능만. 스키마 원본은 레포의 SQL 마이그레이션 파일
- 플랫폼 고유 기능은 `platform/` 어댑터 한 곳에서만 접근한다. 핵심 데이터를 플랫폼 전용 저장소(KV, D1 등)에 두지 않는다
- 배포 설정은 레포에. 새 벤더·기능을 도입할 때 "빼고 옮기려면 무엇을 해야 하나"를 `docs/infra/`에 남긴다

근거 — 예전에 DB 벤더에서 막혀 데이터를 전부 잃었다. 코드는 다시 짜면 되지만 데이터는 복구가 안 된다. 벤더의 백업 기능은 그 벤더가 막히면 같이 막힌다.

반대 의견 — 플랫폼 고유 기능을 직접 쓰면 개발이 빠르고, 추상화 계층은 1인 개발에 부담이다. → 전면 추상화가 아니라 "핵심 데이터는 표준 Postgres, 플랫폼 기능은 한 모듈에서만"으로 비용을 제한했다.

상세 — 교체 지점 표는 아키텍처 5장. 인증의 이전 방법은 `docs/infra/인증선택지_v1` 7장.

미정 — 백업 저장소와 보존 기간, 복구 훈련 주기와 자동화, 배치 실행 위치.

### #20 비용 어뷰징 방어 — 상한은 설계로 건다
비용이 드는 경로마다 제한과 차단 스위치를 둔다. 상세·체크리스트는 `docs/infra/비용어뷰징방어_v1`.

요지:
- 벤더는 지출 상한을 걸어주지 않는다. Cloudflare 예산 알림은 통지 전용이고 다음 날 온다
- 무료 플랜은 넘치면 에러일 뿐 과금이 없다. 공격의 결과가 청구서가 아니라 일시 장애가 되게 한다. **R2만 무료 플랜에서도 초과분이 과금되어 예외** → #33의 9GB 자동 차단
- 비용이 드는 동작은 전부 누가 몇 번 했는지 센다. 익명 쓰기 엔드포인트 없음
- 차단 스위치 `UPLOADS_ENABLED`, `SIGNUP_ENABLED`, `READ_ONLY`, `SEARCH_ENABLED`를 코드 초기부터
- 운영 Worker는 `workers_dev: false`. 공개 재빌드 트리거 없음

근거 — 쿼터 테이블과 차단 스위치는 코드 초기에 없으면 나중에 끼워 넣기 어렵다.

반대 의견 — 유저 0명인데 방어를 먼저 짜는 건 과설계일 수 있다. → 구현은 기능별 체크리스트로 필요 시점에 붙이고, 지금은 규칙과 스키마 자리만 확보한다.

수정 — 원안의 "이메일 인증 전 쓰기 금지"는 #29(소셜 인증 필수 + 가입 단계 Turnstile)로 대체됐다.

### #21 쿼리 도구는 Drizzle. `drizzle-kit push` 금지
스키마 변경은 `drizzle-kit generate`로 SQL 파일을 만들어 커밋한 뒤 적용한다.

근거 — #19의 "스키마 원본은 레포의 SQL 파일". `push`는 이력 파일 없이 DB에 바로 반영하므로 원본이 DB 쪽으로 넘어가고, 다른 Postgres에 같은 스키마를 재현할 근거가 사라진다. Drizzle을 다른 도구(Kysely, Prisma 등)와 비교한 근거는 **원문 미기록.**

이식성 — Drizzle을 빼도 SQL 마이그레이션 파일이 남는다. 교체 비용은 쿼리 코드 재작성뿐이다(아키텍처 5장).

### #22 DB 연결은 Hyperdrive + 표준 Postgres 드라이버
Neon 전용 드라이버를 쓰지 않는다. 연결 문자열은 `platform/db.ts`에서만 읽는다.

근거 — 벤더 전용 드라이버를 쓰면 DB를 옮길 때 쿼리 계층까지 손대야 한다(#19). 표준 드라이버면 연결 문자열만 바꾼다.

제약 — Hyperdrive 무료 일 10만 쿼리. 요청당 쿼리 수를 늘리는 코드(N+1)를 만들지 않는다. 배치 빌드는 Hyperdrive가 아니라 DB 직접 연결로 읽는다.

### #23 요청 제한을 둘로 나눈다
| 대상 | 장치 | 위치 |
|---|---|---|
| IP 단위 폭주 | WAF 속도 제한 규칙 + Rate Limiting 바인딩 | 엣지, `platform/rate-limit.ts` |
| 유저별 쿼터 | DB 테이블 | `services/quota` |

근거 — 앱 레벨 카운터를 어디에 둘지가 걸렸다(일지 2026-09-13 #11). Cloudflare 바인딩은 이식성과 부딪히고, DB에 두면 공격 트래픽이 DB 부하로 옮겨간다. 그래서 IP 제한은 DB에 닿기 전에 바인딩으로(어댑터 뒤에 두어 #19 충족), 유저 쿼터는 인증을 통과한 요청만 도달하는 DB로 나눴다. 바인딩은 위치별로 따로 세어 부정확하므로 쿼터 집계에 쓰지 않는다.

가드 순서 — 차단 스위치 → IP 제한 → 인증 → 유저 쿼터 → 입력 검증. 싼 검사를 앞에 둔다(아키텍처 2장).

### #24 이미지는 게시물에서 독립한 유저 소유 자산
`image`는 유저가 소유하고, 게시물은 `post_images`로 참조만 한다. 갤 공유 시 복제하지 않는다.

`image`가 가진 것 — 소유자, 용량(쿼터 집계), 콘텐츠 해시, 저장 키, 상태(`pending`/`ready`/`deleted`), 검수 상태(`unchecked`/`ok`/`blinded`).

근거 — 사진이 많은 서비스이고, 갤(향후)이 생기면 같은 사진을 복제하지 않고 참조해야 한다(아키텍처 4.4). 쿼터·검수·정리(#25 #33)가 모두 이 테이블의 컬럼 위에서 동작한다.

### #25 고아 이미지는 자동 정리한다
업로드 미완료 또는 미연결 상태로 24시간 → 삭제 표시 → 30일 유예 후 R2 파일 삭제.

부대 조건 — **임시저장은 반드시 서버의 초안(`draft`) 글로 저장**해 사진을 연결해둔다. 브라우저에만 임시저장하면 24시간 뒤 사진이 지워진다.

근거 — 업로드만 하고 글을 쓰지 않는 방식으로 저장소를 채우는 경로를 막는다(#20). 30일 유예는 실수·오판 복구용.

세부 — 연결이 끊긴 시각은 `unlinked_at`에 기록해 24시간 시계를 시작한다. 같은 유저가 같은 파일을 다시 올리면 기존 행을 재사용한다. 유저 간 중복 제거는 하지 않는다. 수명 주기 그림은 아키텍처 4.4.

### #26 이미지 변환은 브라우저에서, 검증은 서버에서
브라우저가 리사이즈·재인코딩하고(이 과정에서 EXIF 제거) 변형본도 만든다. 업로드는 Worker를 거쳐 **R2에 쓰기 전에 파일 헤더로** 포맷·용량·해상도·메타데이터(EXIF/XMP) 부재를 검증한다. R2 직접 서명 URL 경로는 만들지 않는다.

근거 —
- Cloudflare Images 무료는 월 5,000회 변환. 작례 20장 기준 월 250개가 한계이고, 유저가 막 들어오는 시점에 막힌다
- Worker 내부 변환은 무료 CPU 10ms·메모리 128MB로 고화소 사진이 불가능
- 별도 변환 서버는 벤더와 운영이 늘어난다
- 브라우저 변환은 비용 0이고 벤더에 묶이지 않는다

반대 의견 — 서버 변환은 EXIF 제거가 확실히 보장되고 화질이 일정하다. 브라우저는 조작할 수 있다. → 보장은 서버 헤더 검증으로 대신한다. 변조된 클라이언트가 원본을 보내도 R2에 닿기 전에 거부된다.

보조 경로 — 화질·호환 문제가 실제로 생기면 Cloudflare Images를 `platform/` 어댑터 뒤에 보조로 붙인다.

### #27 스타일링은 Tailwind CSS v4 + CSS 변수 토큰
색·간격·글꼴·반경은 `src/styles/`의 CSS 변수 토큰으로만 정의하고, 컴포넌트는 토큰 클래스만 쓴다. 유저 글 본문은 typography 플러그인(`prose`).

근거 — 코드를 쓰는 AI가 둘이다(메인 세션, Antigravity의 킷 페이지). 클래스 이름을 각자 짓게 두면 스타일이 갈라진다. Tailwind는 AI가 가장 일관되게 쓰는 문법이다. 블로그 스킨(1.1.5)은 토큰만 참조하면 변수 교체로 끝난다.

반대 의견 — Astro 스코프 CSS는 의존성 0, 이식성 최상. → CSS는 벤더 잠금이 아니라 빌드 도구라 #19 위험이 작다. 토큰이 CSS 변수라 Tailwind를 빼도 토큰은 남는다.

### #28 인증은 Better Auth 직접 운영
유저·세션·연결 계정 테이블은 우리 Postgres에 둔다. 제공자 고유 ID는 **연결 계정 테이블에만**, 도메인 테이블은 `users.id`만 참조한다.

근거 — 과거 DB 벤더에서 데이터를 잃었다(#19). 유저 테이블이 남의 서버에 있는 Clerk는 이 원칙과 정면으로 부딪힌다. Better Auth는 카카오·네이버·구글을 내장하고 Drizzle 어댑터가 있다. 비용 0.

반대 의견 — Clerk는 로그인 UI·보안 운영·봇 방어를 통째로 맡아준다. 1인 개발자가 인증 보안 패치를 직접 따라가는 건 부담이다. → 라이브러리 버전 업데이트 수준이라 감당 가능하다고 봤다.

제외 — Supabase Auth(네이버 미지원, DB 이원화), Neon 관리형 Better Auth(베타, Neon에 인증까지 묶임), Lucia(개발 중단), Auth.js(유지 모드). 비교표는 `docs/infra/인증선택지_v1` 3장.

조건 — 세션 조회가 요청마다 DB 쿼리를 내지 않게 한다(Hyperdrive 일 10만). 쿠키 캐시 설정의 실제 동작은 구현 시 확인.

### #29 MVP 로그인은 카카오·네이버·구글 소셜 전용
비밀번호 로그인, 가입 인증 메일, 비밀번호 재설정을 만들지 않는다. **같은 이메일이라고 계정을 자동으로 합치지 않는다.** 소셜 추가 연결은 로그인한 본인이 직접 한다.

근거 —
- 무료 Workers에서 비밀번호 해시(순수 JS scrypt, 약 80ms)가 CPU 10ms에 걸린다(Better Auth 이슈 #8860). `node:crypto`로 바꾸면 10ms 안에 드는지는 실측 자료가 없다
- 메일 발송은 Cloudflare 것이 유료 플랜 전용, Resend 무료는 하루 100통. 메일 폭탄 하루에 정상 가입이 막힌다. 소셜 전용이면 이 비용 벡터가 통째로 사라진다
- 한국 커뮤니티에 네이버 로그인은 사실상 필수
- 자동 병합은 이메일 검증이 느슨한 제공자를 통해 남의 계정을 가로채는 경로가 된다

대가와 완화 — 소셜 계정을 잃으면 G-MOIM 계정도 잃는다 → 여러 소셜 연결 허용. 카카오 이메일은 비즈 앱 심사 필요 → 이메일을 식별자로 쓰지 않는다.

#20 대체 — "이메일 인증 전 쓰기 금지"를 "소셜 인증 필수 + 가입 단계 Turnstile"로. 소셜 인증을 거치지 않은 계정은 존재하지 않는다.

### #30 캐시되는 SSR HTML에 로그인 상태·개인화 내용을 넣지 않는다
"OOO님", 내 글 수정 버튼 같은 부분은 island로 빼서 브라우저에서 조회한다. 로그인 쿠키가 있다고 캐시를 우회하지 않는다.

근거 — 작례 페이지는 SSR + Workers Cache(#18)라 캐시된 HTML이 모든 방문자에게 같게 나간다. 개인화 내용이 섞이면 다른 사람에게 내 화면이 나간다. 로그인 유저마다 캐시를 우회하면 그만큼 렌더 비용이 든다.

검증 — 로그인 A로 조회한 뒤 비로그인 B로 같은 URL을 조회해 대조한다(방어 문서 5장).

### #31 에디터는 Tiptap, 본문은 Tiptap JSON
편집 island는 React. 본문은 JSON으로 저장하고 HTML을 저장하지 않는다. 공개 렌더는 서버가 **허용한 노드·마크만** HTML로 바꾸고 목록에 없는 노드는 버린다. 편집기 번들을 공개 페이지에 싣지 않는다.

저장 시 — 본문 이미지 노드에서 `image_id`를 뽑아 `post_images`를 다시 맞춘다. **요청 유저 소유 이미지인지 확인**한다.

근거 — HTML 저장은 XSS 정화가 필요하고, Worker에서 DOM 흉내 라이브러리가 CPU를 쓴다. JSON은 허용 노드만 변환하면 정화가 필요 없고 본문에서 사진 ID를 뽑기도 쉽다. Tiptap은 DOM 없이 JSON을 HTML로 바꾸는 정적 렌더러를 제공한다.

미판정 — Tiptap 버전업으로 JSON 스키마가 바뀌면 저장된 본문이 깨지나. 본문에 스키마 버전을 넣을지 구현 시 판단.

### #32 출력 포맷은 WebP, 안 되면 JPEG. 프리셋 2048/1024/400
| 항목 | 규칙 |
|---|---|
| 파일 선택 | `accept="image/jpeg,image/png,image/webp"`. `image/*`나 `image/heic`를 넣지 않는다 |
| 출력 | 캔버스 WebP → 결과 `blob.type`이 WebP가 아니면 JPEG로 다시 인코딩. 서버는 WebP·JPEG만 받는다 |
| HEIC | 브라우저가 못 열면 거부 + 안내, 거부 건수를 `daily_metrics`에 집계 |
| 프리셋 | 장변 2048(크게 보기) / 1024(본문) / 400(목록·카드). 원본보다 크게 만들지 않는다 |

근거 —
- Safari는 WebP 요청에 **에러 없이 PNG를 준다.** 결과 타입을 확인하지 않으면 무거운 PNG가 올라간다
- WASM 인코더(jSquash, 약 250KB)로 통일하면 폰에서 수십 장 변환이 느려진다. JPEG 폴백의 저장량 증가(약 1.3배 추정)를 감수했다
- 파일 선택을 명시 타입으로 두면 iOS가 HEIC를 JPEG로 자동 변환해 넘긴다. 걸리는 건 윈도우 Chrome 등으로 HEIC 파일을 옮긴 경우

반대 의견 — HEIC 거부는 CLAUDE.md 실패 패턴 "유저에게 단계를 하나 더 요구"에 해당한다. → 인정. 거부 건수를 세서 많으면 변환 라이브러리를 붙인다.

### #33 업로드 쿼터와 전체 저장량 자동 차단
| 항목 | 초기값 |
|---|---|
| 신규 계정 (가입 7일 미만) | 일 50장 · 총 300MB |
| 일반 계정 | 일 200장 · 총 2GB |
| 글당 사진 | 50장 |
| 변형본 크기 상한 | 2048: 3MB · 1024: 800KB · 400: 150KB |
| **전체 저장량** | `image.byte_size` 합계 9GB에서 업로드 자동 중지 |

수치는 `services/quota` 한 곳에만 둔다. 사진 한 장 변형본 합계(추정 WebP 0.7MB·JPEG 1MB)를 실측한 뒤 조정한다.

근거 — R2는 무료 플랜에서도 10GB 초과분이 과금된다. 차단 스위치는 재배포가 필요하고 예산 알림은 다음 날 온다. DB 합계로 즉시 막는 것만이 청구서를 원천 차단한다.

반대 의견 — 9GB 차단은 공격이 아니라 **정상 성장에도** 업로드를 멈춘다. → 멈추는 게 과금보다 낫다. 인프라확장플랜의 8GB 트리거에서 유료 전환을 먼저 판단한다.

미판정 — 신규 일 50장이 네이버 블로그에서 옮겨오는 모델러의 첫날 몰아 올리기를 막나(5장).

### #34 게시 상태는 초안·공개·비공개, 삭제는 30일 휴지통
| 상태 | 누가 보나 | 캐시 |
|---|---|---|
| `draft` | 본인. 임시저장도 draft 글로 (#25) | 안 함 |
| `published` | 전체 | Workers Cache |
| `private` | 본인 | 안 함. 캐시 경로를 타지 않는다 (#30) |
| `deleted_at` 있음 | 본인 휴지통. 30일 후 영구 삭제 → 사진은 연결 해제되어 #25 흐름으로 | 무효화 |

예약 발행은 두지 않는다.

비공개 글의 사진 URL은 **비밀이 아니다.** 해시 키라 추측은 불가능하지만 URL을 받은 사람은 볼 수 있다. 비공개 설정 화면에 안내한다.

근거 — `draft`는 임시저장을 서버 초안으로 하라는 #25의 조건에서 나온다. `draft`·`private`을 캐시하지 않는 것은 #30. 비공개 상태를 둔 이유, 휴지통 기간을 30일로 한 이유, 예약 발행을 뺀 이유는 **원문 미기록.**

## 5. 검토 필요 항목

v3를 쓰면서 결정끼리 맞춰보다 드러난 것. **여기서 고치지 않았다.** 해당 설계 노드에서 판단한다. 영향이 큰 순서.

### 5.1 결정 간 긴장

**① 이미지 URL 불변·긴 캐시(부록 C) ↔ 블라인드·임시조치(부록 A·B)**
이미지 URL은 해시 기반 불변이고 CDN에 오래 캐시된다. 사진을 블라인드하거나 임시조치해도 R2 파일과 CDN 캐시가 남아 있으면 URL로 계속 열린다. 블라인드는 DB 상태값만으로는 성립하지 않고 R2 파일 이동·삭제와 CDN 캐시 무효화가 함께 필요하다. 불법촬영물 신고 대응(부록 B)도 같은 경로를 탄다. → 2.2 신고·임시조치 설계 때.

**② 킷·기체 SSG 일 1회 갱신(#18) ↔ 비공개 전환·삭제·블라인드(#34, 부록 A)**
작례를 비공개로 돌리거나 지워도, 킷·기체 정적 페이지 갤러리에는 다음 배치까지 최대 하루 남는다. 비공개 사진 URL은 비밀이 아니므로(#34) 그대로 열린다. 임시조치의 시한 요건과 하루 지연이 양립하는지 확인해야 한다(부록 B 변호사 검토 항목에 추가). → 7.1 로드맵 전 또는 2.2.

**③ 개인화는 island로(#30) ↔ 요청 한도(#18 #22)**
로그인 유저가 작례를 볼 때 캐시된 HTML 1회 + island의 로그인 조회 API 1회로 Worker 요청이 둘이 되고, 세션 조회가 쿼리를 내면 Hyperdrive 쿼리도 는다. 일 10만 요청을 작례 조회와 나눠 쓴다. 비로그인 조회는 영향 없음. → 구현 시 island 조회를 페이지당 한 번으로 묶고 실측.

**④ 댓글은 블로그에(#2) ↔ MVP에서 갤 제외(#11)**
댓글 모델이 1.2.2(글·댓글·추천, MVP 제외 노드)에 묶여 있고 3장에 댓글 테이블이 없다. MVP 블로그에 댓글이 있는지 정해진 적이 없다. 댓글이 들어가면 쓰기 API·쿼터·신고 대상이 하나 는다(#20). → 0.4 성공 기준 또는 7.1 로드맵에서.

**⑤ 신고 창구는 MVP 포함(#11) ↔ 설계 없음**
2.2가 "요건 파악, 설계 미정"이고 3장에 신고 테이블이 없다. 법적 요건(부록 B)이라 공개 전에 있어야 한다. 방어 문서는 신고에 Turnstile과 유저별 신고 한도를 걸어두었다. → 7.1 로드맵에서 공개 전 필수로 배치.

**⑥ 신규 계정 일 50장(#33) ↔ 초기 모델러 이주(부록 D, 1.1.4)**
네이버 블로그에서 옮겨오는 모델러는 첫날 수백 장을 올린다. 콜드 스타트의 유일한 대체 불가 자산(부록 D)이 첫날 쿼터에 막힐 수 있다. 1.1.4 이관이 보류라 지금은 수동 업로드만 해당. → 1.1.4 재개 시, 또는 운영자가 개별 계정 쿼터를 올리는 수단을 둘지.

**⑦ 전체 저장량 9GB(#33) ↔ 백업 저장소 미정(#19)**
9GB는 `image.byte_size` 합계로 계산한다. DB 백업을 R2에 두기로 하면 백업 용량이 R2 10GB에 함께 잡히는데 이 합계에는 빠진다. → 백업 저장소를 정할 때 R2 밖으로 두거나, 차단 기준을 R2 실사용량으로 바꾼다.

### 5.2 기록 문제

**⑧ #13의 "ISR"은 #18로 사라졌다**
STATUS의 #13 요약에 "SSG/ISR/SSR/CSR"이 남아 있으나 현재 구성에 ISR은 없다. 요약 문구를 고칠지.

**⑨ #11·#12가 STATUS에 "v2 반영"으로 적혀 있으나 v2 본문에 없다**

**⑩ 근거 원문이 없는 결정**

## 부록 A. AI 모더레이션 초안 (미확정)

법적 의무는 AI로 대체되지 않는다. 임시조치는 판단이 아니라 절차이므로 접수·조치·공시·기한·이의신청 경로가 시스템에 있어야 한다. AI가 못 잡아도 절차가 있으면 법적으로는 성립하고, 반대는 성립하지 않는다.

자동 삭제는 최소화하고 자동 블라인드 + 사람 확인 + 사유 표시로 간다. 삭제 주체가 AI면 항의 대상이 없어 분쟁이 커진다.

| 단계 | 대상 | 비용 |
|---|---|---|
| 0 | 업로드 제약, EXIF 제거, 파일 타입·크기 제한 | 0 |
| 1 | 사전·정규식. 초성체·자모분리·특수문자 우회 정규화 후 매칭 | 0 |
| 2 | 애매한 건만 소형 모델 분류. 이미지 NSFW는 오픈소스 셀프호스팅 | 낮음 |
| 3 | 신고된 글 + 2단계가 넘긴 것만 LLM 맥락 판단 | 높음 |

핵심은 전수 검사를 하지 않는 것. 신규·저신뢰 계정만 전수, 이력 쌓인 유저는 샘플링 또는 신고 기반.

v3 참고 — 0단계는 #26·#32·#33으로 확정됐다. 이미지 블라인드는 `image.moderation_status`(#24)에 자리가 있으나 불변 URL과의 관계는 5장 ①. LLM 호출은 비용 벡터라 방어 문서 2장 #9의 제한을 따른다. MVP에는 AI 모더레이션이 없다(#11).

## 부록 C. 비용 구조 방침

이미지 커뮤니티가 돈으로 망하는 원인은 저장 용량이 아니라 **전송량(egress)**이다.

1. **egress 무료 스토리지.** Cloudflare R2. 이 선택 하나가 비용 곡선의 기울기를 결정. S3 호환 API만 사용(#19)
2. **원본을 받지도 서빙하지도 않는다.** 브라우저가 장변 2048 / 1024 / 400으로 줄이고 WebP(안 되면 JPEG)로 재인코딩해 올린다(#26 #32). 원본은 서버에 오지 않는다. 사진 한 장 변형본 합계 추정 WebP 0.7MB·JPEG 1MB(실측 전)
   — v2의 "WebP/AVIF 변환, 원본은 콜드 스토리지 격리" 안은 이것으로 대체됐다
3. **CDN 캐시 히트율 관리.** 이미지 URL 불변 설계(콘텐츠 해시 키), 긴 캐시 헤더. 사이즈 변형은 유한한 프리셋으로 고정. 이미지 도메인은 쿼리스트링 무시(#20)
4. **크롤러 차단.** AI 학습 크롤러가 대역폭만 소모. robots.txt + 봇 차단 + 핫링크 방지(referer)
5. **scale-to-zero 서버.** 초기 유휴 시간이 대부분이므로 상시 VM은 순손실 → Cloudflare Workers(#17)
6. **검색은 Postgres.** pg_bigm / pg_trgm. Elasticsearch는 상시 메모리 비용이 큼
7. **DB 단일 인스턴스 유지.** 조기 샤딩 금지
8. **상한은 설계로 건다.** 무료 플랜을 자연 상한으로 쓰고, 무료에서도 과금되는 R2는 전체 저장량 9GB 자동 차단(#20 #33). 유료 전환은 인프라확장플랜 트리거(일 7만 요청, R2 8GB)에서 판단
9. **렌더 비용은 페이지 성격별로.** 킷·기체는 정적 파일이라 조회 무료, 작례는 캐시 적중도 요청 한도를 쓴다(#13 #18)

목표는 비용을 0으로 만드는 것이 아니라 기울기를 낮추는 것.

## 부록 F. SEO 및 발견성

### 전제

SEO는 **초기 유입 경로가 아니다.** 결정 #5의 noindex 방침과 순환 관계에 있다. 작례가 붙어야 색인되고, 작례를 올리려면 사람이 있어야 하고, 사람은 검색으로 오는데, 검색은 색인이 돼야 한다. 이 순환은 부록 D의 관계 구축으로 깨야 한다.

국내 검색 환경도 불리하다. 건프라 정보 검색은 네이버 블로그·카페와 유튜브가 상위를 점유하고 있고, 신규 도메인이 진입하려면 최소 수개월에서 1년이 걸린다.

그럼에도 지금 설계하는 이유는 **나중에 붙이기 어려운 축**이기 때문이다. URL 구조와 렌더링 방식은 뒤늦게 바꾸면 그동안 쌓인 링크와 색인이 전부 날아간다.

### 지금 반영할 것

1. **URL은 슬러그로.** `/kit/mg-sazabi-ver-ka`, `/unit/rx-78-2`. `slug_history` 테이블로 변경 이력을 남겨 구 URL 리다이렉트를 보장
2. **킷·기체·작례 페이지는 서버에서 HTML을 만든다.** 킷·기체는 SSG, 작례는 SSR + 캐시(#13 #18). 클라이언트 렌더링은 크롤러가 빈 페이지를 본다. 글쓰기·관리만 CSR
3. **구조화 데이터.** 킷 페이지에 Product, 작례에 ImageObject/CreativeWork. URL과 달리 나중에 붙여도 위험하지 않음
4. **noindex 해제 조건은 계산 컬럼으로.** 작례 1개 기준은 잠정. 실데이터를 보고 조정할 수 있게 `is_indexable`로 두고 하드코딩하지 않음
5. **기체 페이지가 주력 SEO 자산.** 사람들은 킷명보다 기체명으로 검색한다. RX-78-2 페이지가 킷 페이지보다 두껍고 색인 가치가 높다. 결정 #6의 부수 효과
6. **공개 전까지 사이트 전체 noindex** (#12). `draft`·`private` 글은 공개 후에도 색인·캐시 대상이 아니다(#34)
7. **캐시된 HTML은 누구에게나 같다** (#30). 크롤러와 로그인 유저가 같은 HTML을 받으므로 개인화 분기로 인한 색인 불일치가 생기지 않는다

### 내부 발견성 (초기부터 작동)

`post_kits` 참조를 거는 진짜 근거는 SEO가 아니라 이쪽이다. 킷으로 묶이지 않으면 작례를 찾는 축이 작성자 이름뿐이고, 그러면 이미 아는 사람만 찾을 수 있다. 신규 유저에게 통로가 없다.
