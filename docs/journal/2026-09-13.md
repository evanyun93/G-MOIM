## #8. 재빌드 딜레마는 틀린 전제 위에 있었다

**상황**
4.1.2 재생성 트리거. STATUS에는 "Pages 빌드 월 500회라 작례마다 재빌드하면 넘는다. 갤러리를 클라이언트에서 불러오면 색인이 안 된다"는 딜레마로 적혀 있었다.

**선택**
킷·기체는 SSG + 일 1회 배치 재빌드. 작례는 SSR + CDN 캐시, 수정 시 태그 무효화. 프레임워크는 Astro(캐시 동작 PoC 통과 조건).

**당시 근거**
공식 문서를 다시 확인하니 500회 한도는 Pages Git 연동 빌드에만 걸리고, 정적 에셋 요청은 무료·무제한에 Worker를 호출하지 않았다. 대신 배포당 정적 파일 2만 개(무료) 한도가 있어 작례까지 SSG로 만드는 건 원래부터 불가능했다. 작례를 자기 URL에서 서버 렌더링하면 색인 문제도 사라진다. Astro는 Cloudflare가 인수했고 페이지별 prerender와 CDN 캐시 제공자가 있다.

**반대 의견**
Next.js(OpenNext) — ISR이 성숙하고 에디터 같은 인터랙션 UI에 강하다. 하지만 ISR 페이지도 매 요청 Worker를 거쳐 무료 요청 한도를 소모한다. 결정 #13의 목적과 충돌.

**미판정 질문**

- Astro Cloudflare 캐시 제공자는 아직 실험 단계다. 캐시 적중 시 정말 Worker가 호출되지 않나. PoC로 확인 예정
- 킷 페이지 갤러리가 하루 늦게 갱신되는 게 유저에게 문제가 되나. "내 작례가 킷 페이지에 안 보인다"는 문의가 오나
- 한도 수치 자체는 맞았는데 어느 제품에 걸리는 한도인지를 잘못 읽고 딜레마를 세웠다. 벤더 한도를 설계 근거로 쓸 때 적용 대상까지 확인하는 습관이 필요한가

## #9. 이식성을 원칙으로 올렸다

**상황**
Cloudflare + Astro로 가기로 하면서 플랫폼 결합이 깊어진다. 인프라가 막혔을 때 옮길 수 있는가.

**선택**
이식성을 결정 #19로 확정하고 CLAUDE.md 절대 제약에 넣었다. 핵심은 DB를 벤더 밖에 매일 백업하고 실제로 복구해보는 것. 플랫폼 고유 기능은 어댑터 모듈 한 곳에서만 쓴다.

**당시 근거**
예전에 DB 벤더에서 막혀 데이터를 전부 잃은 적이 있다. 코드는 다시 짜면 되지만 데이터는 복구가 안 된다. 벤더의 백업 기능은 그 벤더가 막히면 같이 막힌다.

**반대 의견**
플랫폼 고유 기능(KV, D1, 바인딩)을 직접 쓰면 개발이 빠르고 무료 한도 안에서 성능도 좋다. 추상화 계층은 1인 개발에 부담이고, 실제로 옮기는 날이 안 올 수도 있다. → 전면 추상화가 아니라 "핵심 데이터는 표준 Postgres, 플랫폼 기능은 한 모듈에서만"으로 비용을 제한했다.

**미판정 질문**

- 복구 훈련을 실제로 정기적으로 하게 될까. 자동화하지 않으면 안 할 것 같다
- 어댑터 모듈 규칙이 구현 중에 조용히 무너지지 않을까. 린트로 막아야 하나
- 이미지(R2)는 S3 호환이라 옮길 수 있다고 봤는데, 수십 GB가 쌓인 뒤의 이관 시간과 비용은 계산해본 적이 없다
