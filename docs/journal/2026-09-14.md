## #14. 스타일링은 Tailwind v4, 색은 CSS 변수 토큰으로만

**상황**
4.1.5. 후보는 Tailwind v4, Astro 스코프 CSS + CSS 변수(도구 없음), UnoCSS.

**선택**
결정 #27. Tailwind v4. 색·간격·글꼴은 `src/styles/`의 CSS 변수 토큰으로만 정의하고 컴포넌트는 토큰 클래스만 쓴다. 글 본문은 typography 플러그인.

**당시 근거**
코드를 쓰는 AI가 둘이다(메인 세션, Antigravity의 킷 페이지). 클래스 이름을 각자 짓게 두면 스타일이 갈라진다. Tailwind는 AI가 가장 일관되게 쓰는 문법이다. 블로그 스킨(1.1.5)은 컴포넌트가 토큰만 참조하면 변수 교체로 끝난다.

**반대 의견**
스코프 CSS는 의존성이 0이고 이식성이 가장 높다. Tailwind는 마크업이 길어지고 빌드 도구가 하나 는다. → CSS는 벤더 잠금이 아니라 빌드 도구라 #19 위험이 작다고 봤다. 토큰이 CSS 변수라 Tailwind를 빼도 토큰은 남는다.

**미판정 질문**
- "색 값 직접 쓰기 금지"를 AI가 실제로 지키나. `bg-[#...]` 임의값은 Tailwind가 막지 않는다. 린트로 강제해야 할 수 있다
- 유저가 쓴 글 본문(`prose`)과 사이트 UI 토큰이 스킨 교체 시 같이 바뀌나, 따로 노나

## #15. 인증은 Better Auth 직접 운영, 로그인은 소셜만

**상황**
4.6. 후보는 Better Auth 직접 운영, Neon 관리형 Better Auth, Clerk, Supabase Auth. 로그인 수단은 소셜 전용 / 소셜 + 이메일 일회용 코드 / 소셜 + 비밀번호.

**선택**
결정 #28~#30. Better Auth를 우리 Postgres에 붙여 직접 운영. MVP는 카카오·네이버·구글 소셜 전용. 캐시되는 HTML에 로그인 상태를 넣지 않는다.

**당시 근거**
- 조사하다 **무료 Workers에서 비밀번호 해시가 CPU 10ms에 걸린다**는 걸 알았다(Better Auth 이슈 #8860). 비밀번호를 넣으려면 실측부터 해야 한다
- 메일 발송은 Cloudflare 것은 유료 플랜 전용, Resend 무료는 하루 100통 상한. 메일 폭탄 한 번이면 그날 가입이 막힌다. 소셜 전용이면 이 비용 벡터가 통째로 사라진다
- 과거에 DB 벤더에서 데이터를 잃었다(#19). 유저 테이블이 남의 서버에 있는 Clerk는 이 원칙과 정면으로 부딪힌다
- 한국 커뮤니티에 네이버 로그인은 사실상 필수인데 Supabase는 미지원, Clerk는 연결이 어려울 수 있다

**반대 의견**
Clerk는 로그인 UI·보안 운영·봇 방어를 통째로 맡아준다. 1인 개발자가 인증 보안 패치를 직접 따라가는 건 부담이다. 소셜 전용은 소셜 계정을 잃은 유저를 구제할 방법이 없다. → 소셜 여러 개 연결로 완화. 보안 패치는 라이브러리 버전 업데이트 수준이라 감당 가능하다고 봤다.

**미판정 질문**
- 카카오 비즈 앱(이메일 동의항목) 심사가 개인 개발자에게 실제로 통과되나. 안 되면 카카오 유저는 이메일 없이 산다
- 세션 조회를 쿠키 캐시로 줄이는 설정이 Workers + Hyperdrive 조합에서 제대로 동작하나. 요청마다 쿼리가 나가면 일 10만 한도를 작례 조회와 나눠 쓴다
- 소셜 전용이 가입 전환율을 떨어뜨리나, 오히려 올리나. 모델러 커뮤니티에서 "카카오로 시작하기"에 거부감이 있나
- 비밀번호 로그인 요구가 나오면, 그때 `node:crypto` scrypt가 10ms 안에 드는가

## #16. 에디터·이미지 세부 — Tiptap JSON, Safari는 JPEG, HEIC는 거부, 9GB 자동 차단

**상황**
1.1.3. 본문 저장 형식, Safari가 WebP를 못 만드는 문제, HEIC, 쿼터 수치, 게시 상태를 정해야 했다.

**선택**
결정 #31~#34. Tiptap + JSON 저장. 캔버스 WebP, 안 되면 JPEG. 못 여는 HEIC는 거부하고 건수를 센다. 프리셋 2048/1024/400, 신규 일 50장·300MB / 일반 일 200장·2GB, 전체 9GB에서 업로드 자동 중지. 게시 상태는 초안·공개·비공개 + 30일 휴지통.

**당시 근거**
- HTML 저장은 XSS 정화가 필요하고 Worker에서 DOM 흉내 라이브러리가 CPU를 쓴다. JSON은 허용 노드만 변환하면 정화가 필요 없고, 본문에서 사진 ID를 뽑기도 쉽다
- Safari는 WebP 요청에 에러 없이 PNG를 준다. 라이브러리(WASM)로 통일하면 폰에서 수십 장 변환이 느려진다. 저장량 1.3배를 감수했다
- 아이폰에서 바로 올리면 iOS가 JPEG로 바꿔준다. 걸리는 건 윈도우에 HEIC 파일을 옮긴 경우 정도라고 봤다
- **9GB 자동 차단은 R2 무료 초과분이 과금되기 때문.** 기존 차단 스위치는 재배포가 필요하고 예산 알림은 다음 날 온다. DB 합계로 즉시 막는 게 유일하게 "청구서"를 원천 차단한다

**반대 의견**
- HEIC 거부는 CLAUDE.md의 실패 패턴 "유저에게 단계를 하나 더 요구"에 그대로 해당한다. → 인정. 거부 건수를 세서 많으면 변환 라이브러리를 붙인다
- 9GB 차단은 공격이 아니라 **정상 성장**에도 업로드를 멈춘다. 서비스가 잘될 때 막히는 장치다. → 멈추는 게 과금보다 낫다. 인프라확장플랜 트리거(8GB)에서 유료 전환을 먼저 판단한다

**미판정 질문**
- 사진 한 장 변형본 합계 0.7MB(WebP)·1MB(JPEG)는 추정이다. 도색 디테일이 많은 건프라 사진은 WebP 압축 효율이 떨어질 수 있다
- 신규 계정 일 50장이 "첫날 제작기 몰아 올리기"를 막나. 네이버 블로그에서 옮겨오는 모델러는 첫날에 수백 장을 올린다
- 비공개 글의 사진 URL이 비밀이 아니라는 안내를 유저가 이해하나, 문제로 받아들이나
- Tiptap JSON 스키마가 버전업으로 바뀌면 저장된 본문이 깨지나. 본문에 스키마 버전을 넣어야 하나
