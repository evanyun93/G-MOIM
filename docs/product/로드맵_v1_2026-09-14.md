### #40 근거

- **Neon은 pg_bigm을 지원하지 않는다**(Neon 확장 목록, 2026-09-14 확인). RDS·Cloud SQL은 지원. 4.5를 적을 때 DB 벤더와 대조하지 않았다
- pg_trgm은 Neon·RDS·Cloud SQL 모두 지원해 #19를 충족한다
- pg_trgm은 3글자 단위라 "건담", "자쿠" 같은 **2글자 한국어 검색어는 인덱스 효과가 떨어진다**(구현 시 실측). MVP 검색 대상은 킷·기체·별칭 수천~1만 행 규모라 `LIMIT`을 건 스캔으로 감당 가능하다고 본다
- 작례 본문 검색이 필요해지면 그때 전문 검색 방식을 다시 연다(벤더선택지 2.4)

미확인 — 킷 DB 행 수가 실제로 몇인지(HG 포함 시), 2글자 스캔의 실제 지연. M1 완료 조건에서 잰다.

## 5. 운영자 이관 (#42 #44 #45)

2026-09-14 추가. 모델러를 초대하지 않고 운영자가 첫 모델러가 된다. 기존 네이버 블로그 작례 **약 100개, 글당 사진 약 40장**(사용자 추정)을 옮긴다. 원본 사진 파일은 있지만 다시 편집해야 해서 **네이버에 올라간 사진을 받아 쓴다.**

| 항목 | 규칙 |
|---|---|
| 방식 | **운영자 전용 로컬 이관 스크립트.** 일반 유저 기능이 아니다 |
| 검증 | 스크립트가 리사이즈·재인코딩(EXIF 제거)을 로컬에서 하고, **일반 업로드와 같은 API·같은 서버 헤더 검증**을 거친다. 검증을 우회하는 R2 직접 쓰기를 만들지 않는다 |
| 본문 | 네이버 글 HTML → Tiptap JSON 변환. 허용 노드(#31)에 없는 요소는 버린다 |
| 쿼터 | 운영자 역할은 유저 쿼터 예외(#44). **전체 9GB 차단은 적용** |
| 킷 연결 | 이관 후 운영자가 확인하며 건다(#10) |
| 원본 글 | 네이버 원본을 남길지·지울지·링크를 걸지는 미정. 같은 글이 두 곳에 있으면 검색엔진이 한쪽만 색인할 수 있다 |

### 이관 방법 `[초안]`

1. 글 목록 수집 — 블로그의 글 목록을 페이지 단위로 읽어 글 번호를 모은다
2. 글 본문 — 모바일 글 페이지에서 본문 영역(스마트에디터 ONE 구성요소)을 읽는다. 문단·사진·유튜브만 뽑고 나머지는 버린다
3. 사진 — 사진 주소의 크기 지정 파라미터(`?type=w773` 등)를 떼면 올린 크기로 받을 수 있다는 사례가 있다. 로컬에서 리사이즈·재인코딩(EXIF 제거) 후 일반 업로드 API로 올린다
4. 결과 — 초안(`draft`)으로 저장. 운영자가 확인·킷 연결 후 공개

기존 도구(naver-blog-backer)는 구 에디터(v4) 전용이라 현재 글에 맞지 않는다. 직접 스크립트를 짠다. 글 목록·본문 주소 형식은 **M3 착수 시 운영자 블로그로 실제 확인**한다(네이버 내부 주소라 바뀔 수 있다).

주의 — 요청 간격을 두고 천천히 받는다(수천 장). 네이버가 올릴 때 사진을 줄여 저장했다면 2048보다 작은 크기만 나온다(원본보다 크게 만들지 않는다, #32). JPEG를 다시 인코딩하므로 화질이 한 번 더 깎인다.

### 저장량 추정 (실측 전)

| 글 수 | 글당 사진 | 사진 한 장 변형본 합계 | 합계 |
|---|---|---|---|
| 100 | 40 | 0.7MB (WebP) | 약 2.8GB |
| 100 | 40 | 1MB (JPEG) | **약 4GB** |

9GB 차단선(#33) 안에 들어가지만 **R2 무료 10GB의 3~4할을 이관이 쓴다.** 네이버 사진이 2048보다 작으면 줄어든다. 이후 신작·다른 유저 여유가 5GB 남짓이라 인프라확장플랜 8GB 트리거가 앞당겨질 수 있다. 실측 후 아래를 판단한다.
- 이관 대상을 완성작례로 좁힌다
- 이관분에만 가장 큰 변형(2048)을 생략한다
- 9GB 차단선을 올리고 R2 초과 과금(GB당 월 $0.015 수준, 인프라확장플랜)을 감수한다. 차단선은 공격 방어 장치라 없애지 않고 올리기만 한다

구현 시 확인 — 네이버 블로그 사진이 원본 해상도로 받아지는지(표시용으로 축소 저장됐을 가능성), 이관 스크립트가 네이버에 보내는 요청 속도.
