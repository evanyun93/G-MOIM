## 2. 단계별 기준 (#37)

설계에서 반복된 실패 패턴 두 개를 막는 구조다.
- **후행 지표를 초기 조건으로 삼는다** → 검색 유입·조회는 C로 분리, 판정에 쓰지 않는다
- **시점이 다른 조건을 묶는다** → 배포(상시, #12) / 공개(A) / 판정(B)을 따로 둔다

### A. 공개 관문 — 전부 충족해야 홍보·색인을 연다

운영자가 통제할 수 있는 조건만 둔다. 유저 0명이어도 판정 가능.

| 항목 | 기준 | 근거 |
|---|---|---|
| 킷 DB | **MG·RG·PG는 검증 통과**, HG는 목록(제품명·발매연월) 행이라도 전수 | #5 커버리지, #35 입문 유저가 자기 HG를 찾을 수 있게 |
| 운영자 작례 | **M3 완료 후 2달간 운영자가 자기 작례를 G-MOIM에만 올림.** 개수 기준 없음 (#41로 확정) | #5 부속, 상시 기준 |
| 비용 어뷰징 방어 | 체크리스트 5장 전 항목 | #20 |
| 법무 최소 요건 | 신고 창구·임시조치 절차, 개인정보 처리방침, 이용약관 | 부록 B |
| 백업 | 벤더 밖 백업을 **다른 Postgres에 한 번 복구해 행 수 대조 성공** | #19 "복구해봐야 백업" |
| 검토 필요 항목 | v3 5장 중 7.1 로드맵에서 "공개 전 필수"로 분류한 것 | v3 5장 |

### B. 초대 공개 판정 — 블로그 가설

5.2에서 관계를 만든 모델러(부록 D의 5~6명)를 초대해 연다. 판정 대상은 "카페·유튜브에 있는 모델러가 G-MOIM 블로그에 **계속** 올리는가"(#35 미판정 질문).

| 판정 | 조건 (공개 후 8주) |
|---|---|
| **성립** | 초대한 모델러의 **절반 이상**이 작례를 **2개 이상** 올림 |
| **재검토** | 2개 이상 올린 모델러가 **1명 이하** → 카페 대비 블로그 가설(타겟유저 4.1)을 다시 연다 |
| 사이 구간 | 판정 보류. 올리지 않은 모델러에게 이유를 직접 묻는다 |

- 운영자 본인 글은 세지 않는다
- 1개가 아니라 2개인 이유 — 첫 글은 초대에 대한 예의로 올릴 수 있다. 작례 제작에 한 달이 걸리므로 8주에 2개가 "계속 쓴다"의 최소 신호
- 수치는 DB에서 직접 센다(#39). 표본 추정치를 쓰지 않는다
- 댓글이 달렸는지(#38)를 같이 기록한다. 재검토 시 "반응이 없어서 멈췄나"를 가르기 위해

### C. 자연 유입 관찰 — 판정에 쓰지 않는다

| 지표 | 출처 |
|---|---|
| 킷·기체·작례 페이지 조회 (페이지 종류별) | Web Analytics 스냅샷 (#39) |
| 검색 엔진 유입 | Web Analytics 참조 경로 (확인 필요) |
| 비로그인 방문 → 가입 전환 | 가입 수(DB) ÷ 방문(추정). 추정치끼리 나눈 참고값 |
| 초대하지 않은 작성자 수 | DB |

색인은 공개 후 수개월~1년이 걸린다(부록 F). 이 지표가 낮다고 B의 판정을 뒤집지 않는다.

### 상시 — 1순위 목적(포트폴리오·재미)

유저 수와 무관하게 판정한다.

- **운영자가 자기 작례를 카페보다 G-MOIM에 먼저 올리는가.** 운영자 본인이 작례 모델러다(#35). 본인이 안 쓰면 다른 모델러도 안 쓴다
- 일지를 계속 쓰고 있는가 (책 원고 목적)

## 3. MVP 댓글 (#38)

**넣는 이유** — B 판정은 모델러가 계속 올리는지를 본다. 반응이 전혀 없는 곳에 계속 올릴 이유가 없다. #2 "반응이 작품 아래 영구히 쌓여야 아카이브 가치가 생긴다"의 최소형이다. v3 5장 ④의 판정.

| 범위 | 포함 | 제외 |
|---|---|---|
| 구조 | 글 아래 1단 댓글 | 대댓글, 추천·좋아요 |
| 권한 | 로그인 유저 작성. 삭제는 작성자와 글 주인 | 비로그인 댓글 |
| 알림 | 로그인한 글 주인에게 "새 댓글" 표시 | 메일·푸시 |
| 대상 글 | `published` | `draft`·`private` |

규칙:
- **쓰기 API 가드 체인을 그대로 탄다** (#20 #23). 유저별 일일 댓글 수 쿼터, 신규 계정은 낮게. 수치는 `services/quota`에 두며 **초기값 미정**
- 신고 대상에 댓글을 포함한다(2.2)
- 댓글 목록은 공개 내용이라 캐시된 작례 HTML에 넣을 수 있다. 댓글 작성·삭제 시 해당 글의 캐시 태그를 무효화한다(#18). 작성 폼과 "새 댓글" 표시는 island(#30)
- "새 댓글" 표시는 로그인 island가 이미 하는 조회 한 번에 묶는다. 조회를 따로 늘리지 않는다(v3 5장 ③)
- 본문은 일반 텍스트. 링크 자동 변환 정도만. HTML·마크다운 렌더 없음

데이터 모델 `[초안]` — `comment(id, post_id, user_id, body, created_at, deleted_at)`. 글 주인의 마지막 확인 시각은 구현 시 정한다. 설계 문서 다음 버전 3장에 반영.

## 4. 조회 측정 (#39)

킷·기체 페이지는 정적 파일, 작례 페이지는 캐시 적중 시 Worker 코드가 돌지 않는다. **우리 코드로는 조회를 셀 수 없다.**

| 선택지 | 판단 |
|---|---|
| **Cloudflare Web Analytics + 일 배치 스냅샷** | 채택. 무료, 방문자 개인정보 미수집, Worker 요청 0 |
| 자체 비콘 API | 조회마다 Worker 요청 1회 추가(일 10만 한도), 봇 조작에 약함 |
| 조회 지표 없음 | C 단계 관찰 불가 |

규칙:
- 매일 배치가 전날 수치(페이지 종류별 조회, 방문 추정)를 API로 읽어 `daily_metrics`에 저장한다. **보존 기간이 요금제별로 공개돼 있지 않아** 벤더 쪽에만 두면 기록이 사라질 수 있다(#14 소급 불가)
- 조회 데이터는 **표본 추정치**이고 API 데이터셋(`rumPageloadEventsAdaptiveGroups`)은 베타다. B 판정과 쿼터에 쓰지 않는다
- 분석 스크립트 삽입과 배치의 API 호출은 `platform/` 어댑터 뒤에 둔다(#19)
- 개인정보 처리방침에 분석 도구 사용을 적는다

**#14와의 관계** — #14는 "운영 모니터링 자체 구축"이다. 작성·업로드·가입·429 등 우리 코드가 보는 것은 계속 자체 집계하고, 코드가 볼 수 없는 조회만 벤더에서 받아 우리 테이블에 쌓는다. 화면과 기록은 여전히 우리 쪽에 있다.

**옮기려면 (#19)** — 스크립트를 다른 분석 도구(Umami, Plausible 등)로 바꾸고 배치의 읽기 함수를 교체한다. 과거 수치는 `daily_metrics`에 남으므로 이관할 데이터가 없다. 도구가 바뀐 날을 기준으로 수치가 불연속이 되는 것만 기록한다.

구현 시 확인 — 무료 플랜에서 API로 읽을 수 있는 필드(페이지 경로별 조회, 참조 경로), 조회 가능한 과거 범위.
