## 2. 유형별 정의

| 유형 | 하는 일 | MVP에서 쓰는 것 | 로그인 |
|---|---|---|---|
| **작례 모델러** | 도색·개조·제작기 작성. 사진·영상 공급 | 블로그, 에디터, 킷 연결 | 필요 |
| **입문 유저** | 킷 정보 검색, 작례 구경. HG 위주 | 킷·기체 페이지, 작례 조회 | 대부분 불필요 |
| **정보공유 유저** | 리뷰·팁 작성, 기법·도료 정보 | 블로그의 `post_type` 리뷰·팁, `technique`, `post_paints` | 필요 |
| 커뮤니티 유저 (2순위) | 잡담, 질문, 추천, 실시간 반응 | **없음** — 갤 출시 전까지 | — |

운영자 본인은 **작례 모델러**다. 이 유형의 불편은 직접 겪은 것이고, 나머지 유형은 관찰과 추정이 섞여 있다. 초기 운영자 작례(#5 부속)는 본인이 공급한다.

질문 게시(말머리 "질문")는 커뮤니티 유형의 몫이라 MVP에 없다. 정보공유 유저가 질문을 올릴 자리를 찾으면 블로그 `일반` 글로 가게 된다.

## 4. 영향

### 4.1 차별점을 카페 기준으로 다시 봐야 한다

설계 문서 1장의 차별점 표는 디시 갤과 네이버 블로그만 비교한다. 대형 카페는 **게시판(흐름)과 작례 게시판을 이미 한 곳에** 갖고 있어, "흐름과 축적 중 하나만 있다"는 표현이 카페에는 그대로 맞지 않는다.

카페 대비 G-MOIM이 줄 수 있는 것 — **가설, 확인 필요**:

- 작례가 카페 게시판에 흩어지고 **모델러 개인 단위로 모이지 않는다** → 개인 블로그(#1)
- 작례가 **킷·기체 단위로 모이지 않는다** → `post_kits`, 기체 페이지(#6 #10)
- 회원 공개 글은 외부에서 찾기 어렵고, 카페를 떠나면 작례를 가져갈 수 없다 → 슬러그 URL·색인(부록 F), 유저 소유(#24)

→ 설계 문서 다음 버전에서 1장 표에 카페 행을 추가한다. v3 5장 ⑬.

### 4.2 유튜브 모델러 → #36

영상이 주력인 모델러는 글에 영상을 넣지 못하면 G-MOIM에 올릴 이유가 없다. 영상 파일을 직접 받으면 저장·전송 비용과 어뷰징 벡터가 커지므로(#20 #33) 유튜브 임베드만 허용한다.

| 규칙 | 이유 |
|---|---|
| 본문 JSON에는 **영상 ID만** 저장. URL·iframe 속성을 저장하지 않는다 | 허용 노드만 렌더(#31). 임의 URL·속성이 HTML로 나가는 경로를 막는다 |
| 서버 렌더 시 ID 형식을 검사하고(11자, 영문·숫자·`-`·`_`) `youtube-nocookie.com/embed/{id}`로만 출력 | 다른 도메인 iframe 삽입 차단 |
| 영상 노드는 이미지 쿼터·`post_images`와 무관 | 저장 비용 없음 |
| 영상만 있고 사진이 없는 글의 카드·킷 갤러리 이미지 | **미정.** 유튜브 썸네일은 외부 이미지 핫링크라 쓸지 판단 필요 |
| 임베드된 영상도 신고 대상 | 부적절 영상을 넣는 경로 (2.2) |

구현 시 확인 — Tiptap 공식 유튜브 확장이 저장하는 속성(`src` 전체 URL로 저장할 가능성)과 정적 렌더러의 매핑. 확장을 그대로 쓰지 않고 ID만 받는 노드로 감쌀 수 있다. 콘텐츠 보안 정책(CSP)의 `frame-src`에 `youtube-nocookie.com`을 넣고, 개인정보 처리방침에 제3자 콘텐츠(유튜브)를 적는다.

## 5. 미판정

- 대형 카페 모델러가 카페를 두고 **따로 올릴 곳**을 원하나, 카페에 올리고 링크만 걸고 싶어 하나. 후자면 블로그가 아니라 링크 수집이 된다
- 유튜브 모델러는 영상 설명란에 이미 제작기를 쓴다. G-MOIM 글이 영상 설명과 중복 작업이 되지 않나
- 입문 유저가 로그인 없이 킷 DB만 쓰고 떠나면, 그것만으로 MVP 목적에 맞나 (0.4)
